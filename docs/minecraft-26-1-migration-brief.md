2. Loaders: additive modern Fabric/NeoForge pair; `forge` remains the branch ID and means NeoForge for modern leaves. Do not rename old artifact/Gradle identities to neoforge.
3. Names: existing Fabric convention uses officialMojangMappings, not Yarn. No Yarn conversion commit is needed. Target removes the mappings dependency entirely; old leaves retain remapping. Rename ResourceLocation to Identifier only in target code, not ResourceKey indiscriminately.
4. Compatibility: preserve registry IDs, translation keys, recipe IDs, config filenames/keys, peripheral names/Lua method contracts, component keys and important-component removal semantics. Old published binaries remain version-specific. Target Minecraft/CC signature changes require target consumers to recompile; do not promise cross-Minecraft JVM binary compatibility or cross-version network peers.
5. Branch: staged subsystem commits on the assigned implementation worktree, inheriting this cumulative planning commit. Keep 1.20.1 canonical; forward-port old-line fixes deliberately. No push/release or primary-checkout edits.
6. Side: universal mods, including real dedicated servers. Common source can contain gated client APIs (notably Tweakium turtle models); prevent common entrypoint/static initialization from resolving those classes. Fabric client entrypoint and NeoForge client events own initialization.
7. Persistence: existing block-entity settings stay block-entity data; pocket/turtle state stays CC upgrade components/CUSTOM_DATA on modern nodes, `storedData` on legacy. Config stays config, registry entries stay datapack/registry data, fake players/drop-capture caches stay runtime-only. No project-owned SavedData implementation or attachment use was found in authored Kotlin. Therefore no new SavedData file move or attachment conversion is needed. Any future global SavedData must use server storage; dimension-local data stays level-owned, with stable identifiers. The vanilla 26.1 world-layout migration still requires copied worlds and backups.
8. Items: runtime storage/transfer APIs keep mutable ItemStack values. Upgrade definitions/crafting outputs on 26.1.2 use immutable ItemStackTemplate as required by CC's target UpgradeBase; resolve/create stacks only with registry/world context. Preserve copied-template and explicit-removal behavior, not the old signature at all costs.
9. Networking: no project CustomPacketPayload/SimpleChannel registration was found. Existing surfaces are vanilla block-entity update packets (play, server→client) and menu opening data (play, server→client) through MenuBuilder/SavingFunction and loader PlatformToolkit. Port these with bounded registry-aware codecs, explicit buffer ownership and client decode on the appropriate thread. Menu actions/vanilla clicks remain client→server trust boundaries: validate player/menu association, permissions, distances, positions and counts on server. No cross-version wire compatibility or invented custom protocol.
10. Rendering: Tweakium turtle upgrade modelling/RML transforms and Testiarium client/CCT GUI automation are the main custom client surfaces. Resource models/creative tabs also need client validation. No raw OpenGL renderer was found in authored Kotlin searches. Prefer CC target modeller/material APIs and JSON models; do not infer that a server test proves rendering.
11. Datagen: Broccolium provider/sink abstractions, Tweakium upgrade generation and Peripheralium language/model/recipe/loot providers own output. Generated resources and SNBT test structures are part of the port; regenerate through providers, never hand-edit src/generated. NeoForge target client/server datagen split and Fabric provider/output renames are separate adapter concerns.
12. Integrations: CC:Tweaked, Team Reborn Energy, config port where actually used, Kotlin runtimes, loader hooks, access files, Mixins, reflection and Testiarium feature capabilities stay in scope. REI/Mod Menu (Fabric) and JEI (NeoForge) are development/runtime integrations, not excuses to drop required integrations. None is approved disabled. Downstream libraries must exercise public extension points, not just this repository's own content.
13. Toolchain/publication: Java 25 launcher/JDK including jmods for target; retained Java/Kotlin JVM 17 and 21 for old leaves. Wrapper is already Gradle 9.5.0. Preserve site.siredvin coordinates, version 2.0.0 property ownership and loader/common/core suffixes; no release version bump is implied. Build changes and compiler metadata policy below precede gameplay work.
14. Acceptance: build/unit/native/datagen/server/client/copied-save/multiplayer/local-consumer/publication and canonical-restoration gates are specified in the plan. Existing coverage is inherited, not a target pass. Runtime incompatibilities become implementation findings, not retrospective failures of this planning card.

## Transaction and data compatibility contract

Do not translate simulate to a speculative commit. Native NeoForge/Fabric simulation opens a transaction and closes without commit; execution commits only the successful amount, and nested abort restores exact variants/counts/container stack. Preserve component-bearing identity, zero/negative amount rejection, limits, nullable side/context, overflow handling and item/fluid unit conversions. ItemAccess must update the originating slot when a capability operation changes the container item, including abort. Test actual positive providers for item/fluid/energy and failure after partial progress.

The agnostic API is not universally transactional. Cross-storage operations involving legacy/nontransactional backings retain existing bounded guarantees; never certify arbitrary external wrappers as atomic. Reverse wrappers require native transactions or explicit ReplaceableItemStorage on stable backing layout/content. Unsupported restoration must reject before mutation; notification side effects are not promised rollback. Add a typed target-only transaction capability only if required, without weakening existing contracts or claiming simulate/execute is atomic.

Persisted keys include modern `__patch_storage__`, CUSTOM_DATA contents and block-entity settings; legacy `storedData` remains legacy. Preserve missing versus removed components, unrelated patches, failed-encode no-mutation/no-notification and copied template invariants. No auto-delete/rename of old files. New components need immutable values/equality and appropriate persistent/network codecs. Save upgrade means copied-world validation, not guaranteed downgrade. Upgrading vanilla world layout can be irreversible: retain untouched backups and never test against a live world.
